# 密钥泄露事件复盘（2026-09-05）

> 事件等级：**严重（P1）** ｜ 状态：**已闭环** ｜ 涉及仓库：`zsszc/YiCode`（公开仓库）

## 1. 事件概述

在项目早期提交中，以下生产环境敏感信息被提交进了 **公开** GitHub 仓库的 git 历史：

| 泄露项 | 文件/位置 | 风险 |
|---|---|---|
| 阿里云服务器 SSH 私钥 | `aliyun_key.pem`（提交 `fa36b8c` 引入，`83c6740` 删除但历史残留） | 任何人均可克隆历史拿到私钥，直接 SSH 登录 root，**完全控制服务器** |
| 服务器公网 IP | 文档/脚本中硬编码 | 配合私钥可直接定位攻击目标 |
| JWT `SECRET_KEY` 等后端配置 | `.env` 曾入历史 | 可伪造登录态 |

关键教训：**从 git 里删除文件 ≠ 清除泄露**。只要历史里存在过，任何人 `git clone` 后都能找回。

## 2. 时间线

1. 私钥随早期提交进入仓库历史（提交 `fa36b8c`）。
2. 后续提交 `83c6740` 删除了文件，但历史仍然保留。
3. 2026-09-05 安全检查中发现历史残留，确认泄露面。

## 3. 处置过程（已执行）

1. **历史清洗**：使用 `git filter-repo` 从全部历史中抹除 `aliyun_key.pem`、IP 字符串、`SECRET_KEY` 等，随后 `git push --force` 强推覆盖远端。
2. **凭据轮换**（泄露的凭据必须当作已泄露，一律作废）：
   - 阿里云 SSH 密钥对：生成新的 ed25519 密钥对，服务器 `~/.ssh/authorized_keys` 换为新公钥；
   - 后端 `SECRET_KEY`：重新生成并更新服务器 systemd 环境；
   - Kimi API Key：作废旧 key，新 key 仅写入本地 `.env` 与服务器 systemd 配置。
3. **防复发**：
   - `.gitignore` 覆盖 `.env`、`*.pem`（含 `*.pem.pub`）；
   - 服务器启用每日 03:17 自动备份（`/opt/yicode/backups/daily/`，保留 14 份，含数据库）；
   - 建立本文档与 SOP。

## 4. 根因分析

- **直接原因**：开发初期图方便，把部署私钥和环境文件一并提交。
- **流程原因**：没有 secrets 管理规范、没有提交前检查、仓库直接建为公开。
- **认知原因**：误以为"删掉文件再提交"就安全了。

## 6. 经验总结（给未来的自己）

1. **任何密钥、私钥、服务器地址，永远不进 git**。只进 `.env` / systemd / GitHub Secrets。
2. 新仓库默认先建 **私有**，确认无敏感信息再考虑公开。
3. 提交前 `git status` + `git diff --cached` 扫一眼有没有 `.env`、`*.pem`。
4. 一旦泄露：**轮换优先于清理**——先假设攻击者已经拿到并复制了凭据。
